  2. 2取得 SQL

    直接重用既有 SQL

    未命中或不適用Agent 生成 SQL

    先 load_context，再生成

  3. 3驗證與執行

    Guard → Execute

    共用 SQL 驗證
    執行查詢、保存候選
    記錄結果及執行次數

  4. 4判斷結果

    • 有資料檢查通過就回覆；否則修正

SQL 與上下文

先給足必要資訊，減少來回補問

Fast Path：直接重用

命中既有 SQL 且 Scope Gate 通過，就跳過 SQL 生成。比對、Gate 與後續執行仍要計入耗時。

參數化範本是可選延伸，與既有 SQL 重用不同。

Agent：載入後生成

一次提供相關 schema、join、指標規則、欄位真實值及少量 SQL 範例。資訊不足才檢索或 preview。

獨立載入可並行；快取依版本、更新時間及存取範圍失效。

準確度的依據

把問題對齊到指標公式、條件值、日期、資料粒度與 join。例如「台灣」必須由可信字典映射到 TW；不能靠模型猜值。查詢意圖可與 SQL 一起產生，不必增加獨立 LLM 節點。

結果與空值判斷

能執行 ≠ 有資料 ≠ 回答正確

觀察到什麼接下來做什麼
有資料檢查主題、分組、分母、日期及 join 語意；需要修正時附報告 nudge。
0 列／異常 NULL先診斷原因；不能直接算成功或失敗。
COUNT = 0確認查詢符合問題後，可以直接回答零。
SQL 錯誤可修正的欄位、型別等問題才送 Agent；暫時連線錯誤在預算內重試原查詢。

空結果，依序確認四件事

  1. 條件值實際欄位值或可信映射是否正確？
  2. 日期相關資料是否涵蓋指定期間？
  3. 條件組合哪個條件加入後沒有匹配？
  4. Join關聯鍵與連接語意是否正確？

先用已有 metadata，必要時做有限次數的存在性查詢。全表 MAX 日期不保證特定產品有資料；allow_empty_result 也不能取代診斷證據。

有證據可修正 → 修復；確認無資料 → 說明；證據不足 → 無法確認。
不為了產生資料而改年份、地區或產品。診斷探查仍須保留權限範圍，且受查詢次數與 timeout 限制。

Agent 如何修復

同一個 agent_llm_call 的下一輪

  • 從 Agent Path 進入沿用本次已載入的 context，補上 SQL、錯誤或 checks 報告。
  • 從 Fast Path 進入先 load_context 一次，再帶入原問題、SQL 與失敗證據。
  • 仍缺必要資訊在預算內檢索或 preview，取得證據後再生成。

示例：台灣今年的營收

SQL
country = 'Taiwan'
結果
0 列
證據
可信字典確認台灣對應 TW
修正
只改國家值，保留時間與指標定義。

重用 context 可省去重新查詢，但下次模型呼叫仍需帶入相關內容，也仍可能產生 token 成本。

實作契約

SQL、執行結果與檢查報告綁定同一候選。回到模型前，每個 tool call 都須有匹配的 ToolMessage，包括 guard 拒絕；多工具同輪呼叫的順序與預算需明確定義。

預算與結束條件

同一次請求共享額度，轉路徑不重置

預算評測起點範圍
SQL 執行1 次初始 + 2 次修復包含 nudge 後重跑。
Nudge最多 1 次觸發的模型與 SQL 照常計數。
Agent LLM最多 5 次含生成、修復及工具往返；Gate 成本另計。
探查／總耗時依評測設定限制 preview、診斷查詢與整次請求期限。

數字尚未定案。每次操作前檢查額度，外部呼叫 timeout 不超過剩餘時間。recursion_limit 只作 graph 步數的最後防線。

任何結束分支，都先檢查可用候選

成功符合問題且通過檢查；合理的零也可成功。
部分結果有結果但仍有疑慮，附上未解決問題。
無資料有證據支持指定條件下無紀錄。
失敗／無法確認無可用候選，或原因尚未釐清。

無工具呼叫、修正失敗或預算耗盡，都不能丟失先前候選。通過機械式檢查也不保證所有業務語意正確。

用什麼案例測

慢但正確、答案錯卻有資料、意外空結果、合理無資料、Fast Path 命中後失敗。

看哪些指標

p50／p95、節點耗時、LLM／SQL 次數、token；答案正確率、錯誤空結果率、修復成功率。

比較原則

固定資料快照、模型配置及相對日期基準，以人工確認的業務答案評分。檢查修復有無改掉問題條件；LangGraph 遷移與行為優化分開比較。先定位失敗類型，再補診斷與預算，最後評估快取和並行。
