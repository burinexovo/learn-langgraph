agent_loop → LangGraph 節點設計草稿

依現有 application/agent_loop/(loop.py / router.py / tools.py / guard.py) 實際邏輯畫出的理想節點劃分——是「如果要用 LangGraph 重寫,節點該怎麼切」的設計圖,不是新邏輯。
這張圖的定位：對應 docs/agent-loop-langgraph-plan.md 的「並排小範圍驗證」計畫—— 現有 agent_loop/（round 6 黃金評測 94%,DA 已在 Streamlit 使用）繼續是驗證基準,不動它。 這張圖是替 src/agent_loop_lg/graph.py（尚未開始寫）打的草稿,把現有手刻邏輯原封不動對應到 LangGraph 的 node/edge,好讓實作時邏輯不漏掉、不用重新發明。

節點 ↔ 現有程式碼對照

圖上節點對應現有程式碼備註
Routerrouter.py: decide_route() Fast Path 候選比對 + _passes_fast_path_gate()(語意二次確認,fail-closed、短逾時)一起算在這個節點內
Fast Pathapi/service.py 呼叫既有 execute_sql 路徑 不經過 Agent Path 的整個 tool-calling 迴圈
load_contextloop.py: _load_system_prompt() 含 _agent_loop_data_profile_text(低基數欄位真實值,修過 CHINA/APAC 誤判)+ sql_history
agent_llm_callloop.py: run_agent_loop() 主迴圈裡呼叫 invoke_foundry_model() 那一段 LangGraph 裡通常搭配 bind_tools(),對應 _TOOL_SCHEMAS
ToolNodetools.py: retrieve_examples / retrieve_instructions / preview_data LangGraph 內建 ToolNode 模式,依 dispatch table 分派
guardguard.py: check_select_only() 唯一防止 hallucinated 非 SELECT 語句碰到 DB 的關卡,execute_sql/preview_data 共用
execute_sqltools.py: execute_sql() attempts 只在這裡累加——重試預算的計數口徑
_is_result_ok 判斷loop.py: _is_result_ok() allow_empty_result 由模型呼叫時主動聲明,不是系統瞎猜「有沒有資料」
mechanized_checkstools.py: check_topic_coverage / check_group_by_null_exclusion /
check_ratio_denominator_convention / check_relative_date_window_uses_data_max		 執行成功後的自動稽核,不是 LLM 主動呼叫的工具——發現問題就「nudge」一次,不算入重試次數
fallbackloop.py: best_success 變數 Nudge 後模型沒有更好結果時,保底回退第一次就成功的答案,不能讓 nudge 反而丟失一個好答案

對照 references/learn-langgraph 的相關概念

  • ToolNode / bind_tools / 手刻 ReAct loop(05_langgraph_tools_and_agent)—— 對應圖上 agent_llm_call ↔ ToolNode 這一組來回,現有 run_agent_loop() 本質上就是手刻的 ReAct loop, 這部分改用 LangGraph 是最直接的對應。
  • 條件邊、迴圈、Command(04_langgraph_control_flow)—— 對應圖上所有分岔(Router 的 fast/agent、guard 的通過/拒絕、_is_result_ok 的成功/失敗、 mechanized_checks 的有無問題),現有程式碼是 while + if/elif 手刻, 這批邏輯改寫成 LangGraph 的 conditional edge 是這次驗證的核心。
  • Checkpointer / thread_id(06_langgraph_memory_checkpoint)—— 現有 trace(每輪 content + tool_calls,手動組 list 寫回 query_log)概念上可以對應到 checkpointer 的狀態快照,但這次不打算換掉——agent_loop_trace 已經驗證能用, 不在「並排小範圍驗證」的範圍內重新設計。
  • Multi-agent / Supervisor pattern(09_langgraph_multi_agent)—— 刻意不採用。現有工具集固定(檢索兩種 + 執行 SQL + 預覽),不是需要多個獨立 agent 分工的場景, 套 supervisor 模式只會增加不必要的複雜度。

刻意不畫進這張圖的東西

  • harness.py、memory.py、replay.py——這些是黃金評測/多輪對話管理用的 外圍工具,不是 agent_loop 本身的決策節點,圖裡故意不放,避免混淆「核心邏輯」跟「測試工具」。
  • Streamlit 整合(run_agent_loop_turn 的追問/reject/knowledge 分流)—— 那一層在 agent_loop 之外,這張圖只畫 run_agent_loop() 本體。
