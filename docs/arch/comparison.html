LangGraph 開發工作流 · 架構草案比較

同一套節點分工，兩種派工方式

架構 A 用固定的「波次（wave）」分派平行工作；架構 A2 從 A 分支出去，改成 「黑板（blackboard）」動態認領。節點怎麼分工（哪些要問 LLM、哪些純 Python） 兩邊完全一樣，差別只在怎麼把工作分給平行的 worker。 下面先看兩張真的組出來、真的跑過的圖，再看差異整理。

優缺點各三點

不是「A2 全面升級」——是不同的取捨：A2 換來的利用率，代價是可重播性跟除錯難度。

A · 波次

優勢
  • +決定性、可重播：同一份輸入重跑，波次分法固定，好除錯
  • +平行是 LangGraph 自己用 Send 管的分支，不用自己刻搶任務邏輯
  • +查靜態的 wave 計畫就知道發生了什麼事
代價
  • −任務時間差很大時，一個長任務會卡住整波，其他人閒置
  • −波與波之間依序跑，下一波不衝突的任務也得等這一波全部做完
  • −沒有真正的動態調度，資源利用率較低

A2 · 黑板

優勢
  • +動態認領，誰先做完誰接下一個——示例中 5 輪 vs 6 輪
  • +更貼近真實部署：worker 本來就是外部各自獨立的 process
  • +衝突處理更精細，只重設真的衝突的 slice，不用整批重派
代價
  • −需要真正支援原子操作的後端（Postgres row lock / Redis SETNX）
  • −除錯較難：要查即時的黑板狀態，不是一張固定的圖
  • −認領順序可能因時間差而不同，較難重播

怎麼選

節點分工、能不能中途卡住問人，兩邊完全一樣。真正的差異在分工的時機： A 是事先把 change 讀過一遍，照「看起來會不會衝突」先分好堆（不是絕對保證不衝突， 只是預判），同一堆才一起做；A2 是全部直接丟上黑板，誰做完誰就去接下一個還沒人碰的。

slice 大小都差不多 → 選 A

固定波次就夠用。換成 A2 那套動態搶任務的複雜度，換不到什麼好處—— 多出來的只有「同樣輸入重跑，誰做哪個 slice 可能每次不一樣」這種除錯上的麻煩。

工作量落差很大、想讓快的人多做一點 → 選 A2

誰先做完誰去搶下一個，不會被同一波裡最慢的那個拖住——示例裡 5 輪 vs 6 輪 就是這個效果的縮影。代價是排程結果不再是決定性的，比較難重播、除錯。

中途卡住問問題

這是這輪討論的重點機制：code_agent 遇到自己不能決定的事，要能跳出去問人， 而且不能擋住同一波其他還在跑的 slice。

A · 真的測過整張真實圖驗證通過

不是只在獨立的小圖測——直接用正式的 DevWorkflowState／merge_wave／ advance_or_finish／human_checkpoint 整條路徑跑一次：三個平行 slice 裡一個卡住問問題，另外兩個照樣跑完，答完之後正確接回 merge_wave， 同波的其他 slice 完全沒被拖累。

A2 · 也真的測過真正平行的 worker 分支，同樣驗證通過

blackboard_dispatch 用 Send 把每個 worker 拆成真正獨立的分支 （blackboard_worker），每個分支一次只認領、只做一個任務；要不要再派一輪由 check_blackboard_progress 在圖的層級決定，跟 A 的 advance_or_finish 同一招。三個平行 worker 裡一個卡在 slice-needs-human 問問題，另外兩個照樣 認領、照樣做完，答完之後正確併回 code_changes，同一批的其他 worker 完全沒 被拖累。

兩邊共同的已知限制code_changes 是整串累加，不是單輪

review 沒過重派時，兩邊都不會重新跑 plan_slices 清空這個欄位—— 因為它用 operator.add 當 reducer，所以是整個對話串累加，不是「這一輪」 的結果。這是故意留白沒修的地方，寫在這裡是為了不讓它悄悄消失。

現在的完成度

三層完成度不一樣，不能用單一百分比帶過。

已驗證

CLI subprocess 機制（labs/）

不設 API key 靠既有登入跑 CLI、跨 process session resume、 --json-schema 強制 needs_clarification 欄位、多個平行 interrupt 互不干擾——全部真的執行測過，不是紙上推演。

已定案

圖的形狀（A / A2 本身）

節點、邊、synthesize_verdict／review_gate 的分工、迴圈怎麼繞——主流程真的跑得通， notebook 裡的斷言全部通過。

還沒做

失敗路徑、真正接上 Claude Code

每個 agent 節點目前都是回傳假字串的 Python stub，重試／衝突分支從沒真的執行過 （因為 stub 永遠回 PASS）。這是刻意的——sketch 定完形狀，接線是下一步。 但接線本身的可行性不是沒把握，兩件事都真的執行、真的檢查過結果，不是猜的： 不設 API key，靠既有 claude login 就能跑 CLI、 跨 process 用 --resume 接續上一輪上下文。 欠的是把這條真的能動的路徑，接進上面這些 stub 節點裡。
