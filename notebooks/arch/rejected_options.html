評估後不採用的選項

這份表格是「部門開發自動化」架構比較(見 notebooks/arch/README.md)的附件—— 不是研究做得不夠、找不到更好的東西,而是兩輪獨立調查(先廣泛掃五大類、再對 7 個 clone 下來的 repo 做程式碼層級的深讀)都指向同一個結論:GitHub 上目前沒有任何工具做到 「切 slice → worktree 隔離平行 → 自動合併驗證 → 確定性收斂判斷」這一整條鏈——這正是部門 既有 harness 跟這裡在設計的 LangGraph 版本(架構 A)要解決、業界目前都還沒解決的部分。 以下是逐一評估過的候選,不建議再花時間重新調查。

研究已收斂,不建議繼續往 GitHub 找。兩輪調查方法不同(第一輪廣泛掃五大類找高星專案, 第二輪對 candidate 做實際程式碼閱讀,不只看 README),結論一致——這是收斂的證據,不是偷懶的 藉口。如果部門之後看到新的候選工具,判準就用下面表格的三個問題:①有沒有自動合併? ②合併衝突/收斂判斷是不是確定性邏輯(不是 LLM 自己決定)?③一次任務啟動後,是不是真的能 「丟著不管」,不用逐輪對話?
