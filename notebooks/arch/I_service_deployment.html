從本機腳本到服務,實際改了什麼

今天：本機腳本
工程師自己的 terminal,自己 checkout 的 repo,langgraph dev
→
langgraph build
同一份圖包成 Docker image
→
langgraph up
API server + Postgres + Redis,對外提供 REST/SDK 介面
→
薄前端
Slack 風格聊天介面,呼叫 API、接住 interrupt

沒有因為「服務化」而自動解決的問題

  • 每次呼叫要對哪個使用者的哪個 repo/分支動手,服務本身不會自動知道——呼叫端(前端) 要把這個資訊當參數傳進去,服務不能假設自己身上有一份固定的 checkout。
  • 執行 code_agent/git push 的地方要嘛是每次請求各自獨立、 用完即丟的工作環境(動態建 worktree),不能是服務自己身上一份共用的目錄——多人同時用, 共用目錄會互相踩到彼此正在改的檔案跟分支。
  • 誰的 git 憑證——服務要嘛用一個服務帳號憑證(要能對應回「這是哪個工程師發起的」 做稽核),要嘛想辦法讓每個使用者用自己的憑證(更安全,但實作複雜得多)。

跟架構 A(本機腳本版)的差異一覽

架構 I(服務化)架構 A(本機腳本)
圖邏輯完全相同—
觸發方式API/SDK 呼叫,可以來自聊天機器人、其他系統終端機打指令

建議的落地順序

先用架構 A(或更保守的 H)在本機把整套迴圈跑順、讓少數工程師實際用過,確認「兩次核准就好」 這個體驗真的解決了痛點,再考慮往這一頁的服務化方向investment——不要為了假設的「以後很多人要用」 提前把憑證管理、多租戶隔離這些基礎設施蓋好,那是等真的有多人使用需求時才該花的成本。
