架構 E

沿用既有 harness,LangGraph 只做外殼服務化

這是「部門開發自動化」架構比較(見 notebooks/arch/README.md)裡的選項 E。 跟架構 A/B/H 不同,這份不是一張新的 LangGraph 執行圖,而是一個策略性的問題:要不要在 LangGraph 裡把「切 slice → worktree 隔離平行 → 合併驗證 → 收斂判斷」這整套邏輯重刻一遍? 部門已經有一套跑得動、踩過真實 bug 修好的 npspo-coding-workflow-setup harness(靠 inner-loop.js 這個 Workflow script,呼叫 Claude Code 自己的 Task/ subagent 機制)在做這件事。這個架構主張:不重做,讓 LangGraph 只當外層。

對齊需求一次、驗收一次——這是三個「可行」架構(A / B / E)共同的底線, 差別只在中間怎麼把程式碼寫出來、複雜度放在哪一層。

LangGraph 在這個架構裡實際新增的價值(harness 現在沒有的)

  • 跨 change 的長期記憶——store 記住「上一輪人工回饋」「這類需求部門過去 的決定」,harness 本身沒有這種跨 run、跨 thread 的記憶機制。
  • 可部署的 API 介面——langgraph build/up 把這個外殼包成一個 服務,讓觸發跟核准可以來自「終端機以外的地方」(例如聊天機器人、其他內部系統),harness 目前 的核准入口是 Claude Code 終端機裡的 /npspo:apply。
  • 統一 human_checkpoint 的核准語意,不管背後是 harness 還是別的執行引擎,人看到 的核准介面長得一樣。

跟架構 A 的差異一覽

架構 E(這份)架構 A
分波/worktree/合併/收斂邏輯沿用既有 harness(JS,inner-loop.js),不重寫在 LangGraph 裡用 Python 重新刻一遍

這條路真正的成本:橋接層不是免費的

「LangGraph 觸發 harness、等它跑完」聽起來一句話,但 harness 目前的完成訊號、卡住訊號 (working-memory.md 裡的「⚠️ 交還給人」段落、state.json 的 last_run_id/script_path)是設計給**人在終端機裡讀**的,不是設計給 另一個程式(LangGraph)去 poll、去解析、去轉換成自己的 interrupt() 語意的。 trigger_harness_run 這個節點要嘛得寫一層「讀 harness 產出的檔案、判斷完成/卡住」 的橋接邏輯,要嘛得改 harness 本身,讓它在完成/卡住時主動呼叫一個 LangGraph 能接住的 webhook/ API——這層橋接工作本身不小,是這個架構省下 wave/merge 邏輯之後,換來的新工作項目,評估時要 算進去,不是「幾乎不用寫東西」。

什麼時候該選這個

  • 部門已經很依賴、很信任現有 harness 的執行品質,不想冒風險換一套新邏輯。
  • 近期真正想解決的是「怎麼讓核准/觸發不綁死在某個人的終端機 session 裡」,而不是「怎麼讓 平行開發邏輯更好」——這正是 E 補的那塊,不是它想解決的問題。
  • 團隊沒有餘力同時維護兩套(LangGraph 版 + harness 版)wave/merge/收斂邏輯,寧可只維護一套。
